# Hardwood: sign-up system for larps with sensitive themes

Invitation-only sign-up for a larp (first event: Hardwood High 1). Invitees answer a vetting
survey, see each other's completed answers, flag each other with colours expressing their
willingness to play together, and the GMs cast players from the result. Personal data is
stored encrypted to audiences (INVITEE, GM, SELF) and decrypted on the server within a
signed-in session. Single-tenant: one deployment per event. Next.js 16 App Router + Prisma 8
(prisma-next) + Bootstrap, living at the repo root.

- What the app does: [docs/spec.md](docs/spec.md)
- How it is built and in which order (milestones, data model, crypto): [docs/plan.md](docs/plan.md)
- Running an event (init, GMs, invites, casting, recovery key, backups): [docs/operations.md](docs/operations.md)

## Working style

- Commit directly on `main` with Conventional Commit messages (`feat:`, `fix:`, `chore:`,
  `docs:` …); the owner pushes and watches CI.
- Never run anything against a non-local database. Locally, `hardwood` is the development
  database and `hardwood_test` the integration-test database.
- The dev server runs on port 3161. When working in a git worktree alongside another checkout,
  run it on another port (`npx next dev --turbopack --port 3162`) and point `PUBLIC_URL` at it.

## Commands

- `npm run dev` – dev server on http://localhost:3161 (no automatic migrations; run `npm run db:migrate:dev` first)
- `npm run build`, `npm run lint`, `npm run typecheck`, `npm run format`, `npm run format:check`
- `npm test` (unit, `*.test.ts`), `npm run test:integration` (`*.integration.test.ts`, migrates and uses `TEST_DATABASE_URL`)
- `npm run db:plan -- <slug>` – emit contract and plan a migration; `npm run db:migrate:dev` – apply and advance the `db` ref
- `npm run db:verify` – check the dev database against the contract
- `npm run init`, `add-gm`, `upgrade`, `rotate-key` – operator tools in `src/bin/` (shared unlock
  and error handling in `unlock.ts`; logic in `src/models/bootstrap.ts`, `upgrade.ts`,
  `rotation.ts`)

## Prisma 8 is not Prisma 7

Read `node_modules/@prisma/orm-postgres/skills/prisma-8/SKILL.md` and its `references/` before
touching the contract, migrations or queries. Key points:

- Contract source: `src/prisma/contract.prisma`. After editing, `prisma contract emit` regenerates
  `contract.json` + `contract.d.ts` (committed, never hand-edited).
- Queries: `db.orm.public.<Model>` and `db.sql.public.<table>` from `src/prisma/db.ts`; raw SQL
  through the `sql` tag in `src/prisma/sql.ts`. Transactions: `db.transaction(async (tx) => …)`
  with `tx.orm.public.<Model>`.
- Timestamps are `TimestamptzString`: rows carry strings (PostgreSQL text format, e.g.
  `2026-10-28 22:11:25.12+01`), and writes take strings. Cross the boundary with `parseDates` /
  `formatDates` from `src/prisma/dates.ts`, and list every new timestamp column there. App-level
  row types (`User`, `EncryptedRecord`, …) with `Date`s are in `src/prisma/models.ts`; enum
  constants in `src/prisma/enums.ts`.
- `Jsonb` columns take a `JsonValue`; convert with `toJson()` from `src/prisma/json.ts`.
- Ids are `@default(uuid(4))`, generated by the runtime on create (no database default), so rows
  inserted with raw SQL need an explicit id.
- The table for `User` is `"user"`, a reserved word: quote it in hand-written SQL.
- Migrations are TypeScript packages under `migrations/app/`; `ops.json` is compiled by running the
  migration file, never edited by hand. `migration plan` chains from the `db` ref
  (`migrations/app/refs/db.json`); always apply locally with `npm run db:migrate:dev` so the ref
  advances, and commit the ref with the migration.
- Production applies migrations with `src/bin/migrate.mjs` (ORM command family only) so the
  migrator image stays small; local development uses the `prisma` CLI.
- Prisma only appends native enum values: add new values at the end of the enum.
- `pg` and `@types/pg` stay pinned to the versions the Prisma runtime bundles. Prisma packages
  are pinned to the same release candidates as edegal and larpit-fi; upgrade them together.
- The CLI's "Prisma agent skills are out of date" warning is expected: skills are read from
  `node_modules`, and `prisma skills sync` is not used here.

## Auth and crypto

- Keys: each user's X25519 private key is stored encrypted under an Argon2id key from their
  password and `KDF_PEPPER` (`User.encryptedPrivateKey`; sign-in moves unpeppered keys over);
  the INVITEE and GM audience keys are sealed to their public key. The GM audience key doubles as
  an X25519 private key whose public half is `Event.gmPublicKey`, so anyone can wrap data keys to
  the GMs. The recovery key (printed once by `npm run init`) unwraps both audience keys from
  `Event`. Primitives live in `src/crypto/primitives.ts`; nothing else touches `node:crypto` for
  data.
- Never seal to a public key read from the database without verifying it. GM wraps use
  `gmPublicKeyFor(keys)` (derived from the GM key, else `GM_PUBLIC_KEY`; the Event row only
  outside production without a pin), and `getViewer` runs `verifyGmKey` for GM sessions. User
  public keys go through `verifiedPublicKey` (`User.publicKeyBinding`, a wrap under a key derived
  from the INVITEE key; `bindPublicKey` when creating or replacing a key pair).
- Records (blob format version 2) are bound to `id|kind|ownerId` as aad and carry `mac`, an HMAC
  under a key derived from the INVITEE key (`recordMac`), so every session can verify that an
  invitee wrote them. `encryptJson` pads plaintexts to 4096-byte blocks. Rotating the INVITEE key
  (`rotate-key`) must recompute macs and bindings, which both derive from it.
- Sessions: the unlocked `Keys` live only in the encrypted `hardwood_session` cookie
  (`src/crypto/session.ts`; pure codec in `sessionCodec.ts`; sliding refresh in `src/proxy.ts`),
  with `authenticatedAt` (kept on refresh; a week's absolute lifetime) and the user's
  `sessionEpoch` at sign-in. `getViewer` rejects a session from an older epoch; password change,
  GM-led reset, Sign Out Everywhere and key rotation move it. Re-issue a session with
  `createSession({ keys, authenticatedAt: viewer.authenticatedAt, epoch })`.
- Viewer: pages and actions start with `getViewer()` / `requireViewer()` / `requireGm()` from
  `src/auth/viewer.ts` (user row, keys, decrypted event settings, display name), then the
  predicates in `src/auth/permissions.ts`. Actions re-check; hiding in the UI is not enough.
- Records: `readRecord(kind, ownerId, keys)` and
  `writeRecord(kind, ownerId, content, audiences, keys, { tx })` in `src/crypto/records.ts`,
  plus `read/writeEventSettings` and `read/writeSurvey`. Content types are in
  `src/models/types.ts`. Users, invites and passwords are in `src/models/user.ts`.
- Never log PII, decrypted content, passwords, tokens, keys or request payloads, and never put
  them in error messages; errors shown to users are translation keys.

## Phases and permissions

- `getPhase(settings, now)` in `src/models/phase.ts` derives `signupOpen`, `previewOpen`,
  `flaggingStarted`/`flaggingOpen`, `practicalStarted`/`practicalOpen` and `castingCompleted`
  from the timeline. A period without a start is closed; one without an end stays open once
  started; flagging starts at `signupEndsAt` unless `flaggingStartsAt` is set; the preview stays
  open after sign-up ends.
- Predicates in `src/auth/permissions.ts` are pure (`ViewerLike` + `now`; a `Viewer` satisfies
  it): `hasAccepted`, `isGm`, `canSeeSignup`, `canEditSignup`, `flaggingMode` (`none`,
  `preview`, `flagging`, `readonly`, `names-only`), `canSeeFlagging`, `canEditFlags`,
  `canSeePractical`, `canEditPractical`, `canSeePrivacy`, `canWithdraw`. The `Viewer` carries
  what they need: `vettingResponse`, `vettingCompleted`, `castingResult` (only once the casting
  is completed) and `hasPracticalResponse`.
- Model functions that write on the viewer's behalf re-check the predicate and throw `Forbidden`
  (`src/models/vetting.ts`); actions map it to `{ ok: false, reason: "forbidden" }`.

## Players and casting

- `src/models/players.ts`: `listPlayers(keys)` decrypts every user's vetting response,
  `PLAYER_ATTRIBUTES`, `FLAGS` and `PRACTICAL_RESPONSE` in memory (one query per kind via
  `readAllRecords` in `records.ts`) into `PlayerRow`s; `setUiStatus`, `updatePlayerAttributes`,
  `createInvites`, `resetPlayerPassword` and `deletePlayer` refuse with `PlayerError(reason)`,
  which the actions return as `{ ok: false, reason }` (translated via `Players.errors`).
- The six-state UI status is pure (`src/models/playerStatus.ts`): plaintext `User.status` plus
  `PLAYER_ATTRIBUTES.castingDecision`; `allowedUiStatuses` encodes INVITED ⇄ REVOKED and
  ENTERED/SELECTED/NOT_SELECTED/WITHDRAWN among themselves. WITHDRAWN keeps the decision.
- `src/models/casting.ts`: `completeCasting` / `revertCasting`, and `recomputeCastingResults`,
  which `setUiStatus` runs while the casting is completed so `CASTING_RESULT` follows status
  changes. Only ENTERED users with a decision get a result; mutual greens come from the pure
  `computeMutualGreens` (`mutualGreens.ts`) over `readAllFlags` (`flags.ts`). A SELECTED result
  also lists `selectedPeers` (the other SELECTED, ENTERED players), since an invitee's session
  cannot read others' decisions; NOT_SELECTED results have empty lists.
- Deletion (WITHDRAWN only) rewrites others' `FLAGS` blobs (`removeFlagsOn`) and
  `CASTING_RESULT.mutualGreens`/`selectedPeers` through the GM wraps, keeping each data key, then
  deletes the user (records cascade).
- Self-withdrawal (`withdraw` in `src/models/withdraw.ts`) runs in the invitee's session, which
  has no GM key, so it cannot recompute others' casting results: after a withdrawal following
  casting completion, others' `selectedPeers`/`mutualGreens` still name the withdrawn player
  until the next GM status change or casting revert/complete. `listFlaggable` filters out
  non-ENTERED users anyway, so the stale id only lingers in the mutual green badges.
- `/players` columns are a `Column<PlayerRow>[]` in `src/app/players/columns.tsx` (order = screen
  order); editable cells are client components in `cells.tsx` that autosave through actions.
  Invite results and reset passwords travel only in the action's return value and are never
  stored or logged.
- `npm run seed:dev` (local databases only; `RECOVERY_KEY` or `--recovery-key` from
  `.dev-credentials.txt`; `--keep-timeline`) adds 24 fake invitees with the password
  `salasana123`, flags, attributes, sample choices and vetting questions; existing handles are
  skipped. `--reset` truncates every table first and initialises the event anew (new recovery
  key, no key needed).

## Flagging

- The flags are defined per event in `EventSettings.flags` (`FlagDefinition { slug, title,
definition }`, screen order), edited on Structure > Choices as `slug: title: definition`
  lines and seeded from `Flagging.defaultFlags` by `initializeEvent`; `readEventSettings`
  substitutes those defaults when the stored list is missing or empty. `src/models/flagDefinitions.ts`
  (pure, client-safe) holds the only slugs with a meaning: `neutral` (absence of a key, must
  exist, `flagDefinitionsSchema` enforces it) and `green` (mutual greens), plus `flagVariant`
  (red/yellow/neutral/green get colours, anything else is grey) and the line parser.
- `src/models/flags.ts`: `listFlaggable(viewer, now)` (other ENTERED users with a completed
  vetting response; in `names-only` mode only the names of those the viewer flagged),
  `readOwnFlags`, `setFlag` (`neutral` deletes the key; a slug not in `settings.flags` is
  `Forbidden`) and `setFlagsCompleted`, which re-check `canEditFlags` and that the target is
  flaggable (`Forbidden`), and write `FLAGS` to SELF + GM with the viewer's own public key.
  `mutualGreensFor(viewer)` reads `CASTING_RESULT`. GM side: `flagMatrix(keys, flags)` and
  `flagsForPerson(keys, userId, flags)` drop slugs the event no longer defines. Pure helpers
  (`isFlaggable`, `summariseTotals`, `initials`) are in `flagSummary.ts`.
- After casting completion a SELECTED viewer's list (and `setFlag` targets) is narrowed to
  `CASTING_RESULT.selectedPeers`; non-selected viewers are in `names-only` mode. Flags changed
  after casting (if the GMs reopen flagging) do not update mutual greens until
  `recomputeCastingResults` runs again.
- `/flagging`: server page → `FlaggingList.tsx` (client; one `setFlagAction` per click) →
  `actions.ts`. `/players/flags` and `/players/flags/[userId]` are GM only and not in the app bar.

## Practical and Privacy

- Sign Up and Practical share `SurveyEditor` (`src/components/SurveyEditor.tsx`: completion
  switch, required-fields warning, `AutosaveSchemaForm`) and the action plumbing in
  `src/app/actions/surveyResponse.ts` (`surveyFormDataSchema`, `guardedSurveySave`).
- `src/models/practical.ts`: `readOwnPractical`, `savePracticalAnswers`, `setPracticalCompleted`
  re-check `canEditPractical` (`Forbidden`) and write `PRACTICAL_RESPONSE` to SELF + GM with the
  viewer's public key, as flags do. `/practical` is a 404 unless `canSeePractical`.
- `/privacy`: the plaintext policy for every signed-in user; for accepted ones a Danger Zone
  whose `ModalButton` posts `withdrawAction` (`src/app/privacy/actions.ts`) → `withdraw(userId)`
  (`src/models/withdraw.ts`, ENTERED only), then redirects to `/signup`.
- `StatusBanner` (root layout): `statusBannerKind` is pure; WITHDRAWN wins over a casting result.

## Forms

- `src/components/forms/` is a stripped port of Kompassi's `kompassi-v2-frontend/src/components/forms/`
  (same file and component names, to keep diffs against upstream readable). Import from the
  `@/components/forms` barrel. Translations: `SchemaForm` and `FormEditor` namespaces (Finnish
  copied from Kompassi); keep them free of functions, they are passed to client components.
- Kept field types: StaticText, SingleLineText, MultiLineText, MarkdownText, NumberField (integer),
  SingleSelect, MultiSelect, RadioMatrix. Stripped: every other field type, dimensions,
  annotations, `encryptTo`, `isKeyField`, `summaryTitle`, `htmlType`, `propagate*`, drafts,
  GraphQL. Titles and help texts are plain strings (single-language surveys).
- `SchemaForm` renders uncontrolled inputs (wrap it in a `<form>`, read with `processFormData`);
  `SchemaFormResponse` is the read-only view; `validateRequired` lists unanswered required fields;
  `FormEditorWrapper` edits a `Field[]` and calls a server action on every change.
- `AutosaveSchemaForm` (written here, not ported) wraps a `SchemaForm` in a `<form>` and calls a
  server action with its `FormData`: debounced on `input`/`change`, flushed on leaving the form,
  `visibilitychange` and `pagehide`, plus a poll of the serialised form that catches changes
  firing no event (MarkdownEditor's hidden input). Actions return `{ ok, savedAt }`. Next.js
  dispatches a client's server actions one at a time, so autosave and other actions on the same
  record do not race within a tab.
- Survey schemas are validated with `fieldsSchema` (`schema.ts`) on save; slugs match
  `^[a-z0-9_]+$`, choice slugs `^[a-z0-9_-]+$`. Choices are edited as `slug: title` lines
  (`parseChoices` / `formatChoices`), also for event attributes in the Structure view.
- Adding a field type: add the interface to the `Field` union and `fieldTypes` in `models.ts`, then
  follow the exhaustiveness errors (`SchemaFormInput`, `processFormData`, `newField`,
  `getFieldEditorFields`, `isAnswered`, `SchemaFormResponse`); add its Zod variant in
  `schema.ts` (a type check there fails until it matches), its `FormEditor.fieldTypes` title in
  both languages and an example in `editFieldForm.test.ts`.

## Conventions

- `src/config.ts` is the only reader of `process.env`. Production refuses to start without
  `DATABASE_URL` and `SESSION_SECRET`.
- Translations: `src/translations/en.tsx` defines the `Translations` type, `fi.tsx` implements it.
  `getTranslations()` returns the event's language (`EVENT_LOCALE`); there is no language switch
  and no locale route segment. Components take narrow `messages` props typed as
  `Translations["Namespace"]`. Finnish must be real, idiomatic Finnish; the first event is in Finnish.
- Bootstrap + SCSS (no Tailwind), react-bootstrap for interactive components, `@con2/components`
  for shared components. Dark theme by default (`theme` cookie, `data-bs-theme` on `<html>`).
- Server components for pages, server actions for mutations (Zod-validated input), client
  components only where interactivity requires.
- All pages are dynamic (they read cookies); nothing with personal data is statically rendered or cached.
- Never log personally identifiable information, decrypted content or request payloads.
- Lowercase SQL keywords in hand-written SQL. Constants in lowerCamelCase. Import via the `@/*` alias.
- Containers must not set the `HOSTNAME` env var. The server binds 0.0.0.0 without it.
