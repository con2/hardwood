# Hardwood: sign-up system for larps with sensitive themes

Invitation-only sign-up for a larp (first event: Hardwood High 1). Invitees answer a vetting
survey, see each other's completed answers, flag each other with colours expressing their
willingness to play together, and the GMs cast players from the result. Personal data is
stored encrypted to audiences (INVITEE, GM, SELF) and decrypted on the server within a
signed-in session. Single-tenant: one deployment per event. Next.js 16 App Router + Prisma 8
(prisma-next) + Bootstrap, living at the repo root.

- What the app does: [docs/spec.md](docs/spec.md)
- How it is built and in which order (milestones, data model, crypto): [docs/plan.md](docs/plan.md)

## Working style

- Commit directly on `main` with Conventional Commit messages (`feat:`, `fix:`, `chore:`,
  `docs:` …); the owner pushes and watches CI.
- Never run anything against a non-local database. Locally, `hardwood` is the development
  database and `hardwood_test` the integration-test database.
- The dev server runs on port 3161. When working in a git worktree alongside another checkout,
  run it on another port (`npx next dev --turbopack --port 3162`) and point `PUBLIC_URL` at it.

## Commands

- `npm run dev` – dev server on http://localhost:3161 (no automatic migrations; run `npm run db:migrate:dev` first)
- `npm run build`, `npm run lint`, `npm run typecheck`, `npm run format`, `npm run format:check`
- `npm test` (unit, `*.test.ts`), `npm run test:integration` (`*.integration.test.ts`, migrates and uses `TEST_DATABASE_URL`)
- `npm run db:plan -- <slug>` – emit contract and plan a migration; `npm run db:migrate:dev` – apply and advance the `db` ref
- `npm run db:verify` – check the dev database against the contract

## Prisma 8 is not Prisma 7

Read `node_modules/@prisma/orm-postgres/skills/prisma-8/SKILL.md` and its `references/` before
touching the contract, migrations or queries. Key points:

- Contract source: `src/prisma/contract.prisma`. After editing, `prisma contract emit` regenerates
  `contract.json` + `contract.d.ts` (committed, never hand-edited).
- Queries: `db.orm.public.<Model>` and `db.sql.public.<table>` from `src/prisma/db.ts`; raw SQL
  through the `sql` tag in `src/prisma/sql.ts`. Transactions: `db.transaction(async (tx) => …)`
  with `tx.orm.public.<Model>`.
- Timestamps are `TimestamptzString`: rows carry strings (PostgreSQL text format, e.g.
  `2026-10-28 22:11:25.12+01`), and writes take strings. Cross the boundary with `parseDates` /
  `formatDates` from `src/prisma/dates.ts`, and list every new timestamp column there. App-level
  row types (`User`, `EncryptedRecord`, …) with `Date`s are in `src/prisma/models.ts`; enum
  constants in `src/prisma/enums.ts`.
- `Jsonb` columns take a `JsonValue`; convert with `toJson()` from `src/prisma/json.ts`.
- Ids are `@default(uuid(4))`, generated by the runtime on create (no database default), so rows
  inserted with raw SQL need an explicit id.
- The table for `User` is `"user"`, a reserved word: quote it in hand-written SQL.
- Migrations are TypeScript packages under `migrations/app/`; `ops.json` is compiled by running the
  migration file, never edited by hand. `migration plan` chains from the `db` ref
  (`migrations/app/refs/db.json`); always apply locally with `npm run db:migrate:dev` so the ref
  advances, and commit the ref with the migration.
- Production applies migrations with `src/bin/migrate.mjs` (ORM command family only) so the
  migrator image stays small; local development uses the `prisma` CLI.
- Prisma only appends native enum values: add new values at the end of the enum.
- `pg` and `@types/pg` stay pinned to the versions the Prisma runtime bundles. Prisma packages
  are pinned to the same release candidates as edegal and larpit-fi; upgrade them together.
- The CLI's "Prisma agent skills are out of date" warning is expected: skills are read from
  `node_modules`, and `prisma skills sync` is not used here.

## Auth and crypto

- Keys: each user's X25519 private key is stored encrypted under an Argon2id key from their
  password (`User.encryptedPrivateKey`); the INVITEE and GM audience keys are sealed to their
  public key. The GM audience key doubles as an X25519 private key whose public half is
  `Event.gmPublicKey`, so anyone can wrap data keys to the GMs. The recovery key (printed once by
  `npm run init`) unwraps both audience keys from `Event`. Primitives live in
  `src/crypto/primitives.ts`; nothing else touches `node:crypto` for data.
- Sessions: the unlocked `Keys` live only in the encrypted `hardwood_session` cookie
  (`src/crypto/session.ts`; pure codec in `sessionCodec.ts`; sliding refresh in `src/proxy.ts`).
- Viewer: pages and actions start with `getViewer()` / `requireViewer()` / `requireGm()` from
  `src/auth/viewer.ts` (user row, keys, decrypted event settings, display name), then the
  predicates in `src/auth/permissions.ts`. Actions re-check; hiding in the UI is not enough.
- Records: `readRecord(kind, ownerId, keys)` and
  `writeRecord(kind, ownerId, content, audiences, keys, { tx })` in `src/crypto/records.ts`,
  plus `read/writeEventSettings` and `read/writeSurvey`. Content types are in
  `src/models/types.ts`. Users, invites and passwords are in `src/models/user.ts`.
- Never log PII, decrypted content, passwords, tokens, keys or request payloads, and never put
  them in error messages; errors shown to users are translation keys.

## Conventions

- `src/config.ts` is the only reader of `process.env`. Production refuses to start without
  `DATABASE_URL` and `SESSION_SECRET`.
- Translations: `src/translations/en.tsx` defines the `Translations` type, `fi.tsx` implements it.
  `getTranslations()` returns the event's language (`EVENT_LOCALE`); there is no language switch
  and no locale route segment. Components take narrow `messages` props typed as
  `Translations["Namespace"]`. Finnish must be real, idiomatic Finnish; the first event is in Finnish.
- Bootstrap + SCSS (no Tailwind), react-bootstrap for interactive components, `@con2/components`
  for shared components. Dark theme by default (`theme` cookie, `data-bs-theme` on `<html>`).
- Server components for pages, server actions for mutations (Zod-validated input), client
  components only where interactivity requires.
- All pages are dynamic (they read cookies); nothing with personal data is statically rendered or cached.
- Never log personally identifiable information, decrypted content or request payloads.
- Lowercase SQL keywords in hand-written SQL. Constants in lowerCamelCase. Import via the `@/*` alias.
- Containers must not set the `HOSTNAME` env var. The server binds 0.0.0.0 without it.
